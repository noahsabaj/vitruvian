### GPU smoke test — the LD_LIBRARY_PATH gotcha

First attempt fell back to CPU:

    RuntimeError: Unable to load cuSPARSE. Is it installed?
    JAX devices: [CpuDevice(id=0)]

**Diagnosis.** The user shell had `LD_LIBRARY_PATH=/usr/local/cuda/lib64:`
pointing at the *system* CUDA 12.8 install. The dynamic linker was
finding the system `libcusparse.so.12` before JAX's bundled
`nvidia-cusparse-cu12` (12.5.10) that ships in the CUDA-12 pip wheels.
The system version mismatched what JAX's CUDA plugin expected, so the
plugin failed its version probe and JAX silently degraded to CPU.

**Fix.** Unset `LD_LIBRARY_PATH` before importing JAX. Confirmed:

    env -u LD_LIBRARY_PATH uv run python -c "import jax; print(jax.devices())"
    # => [CudaDevice(id=0)]

OOM log lines during JAX init (default 75 % VRAM pre-alloc on the 8 GB
card, colliding with ~3 GB already used by Xorg / Cinnamon / Discord)
are cosmetic — JAX scales back and the compute runs correctly.

**Permanent fix.** `scripts/env-setup.sh` unsets `LD_LIBRARY_PATH` and
activates the uv venv; source it once per shell before running anything
GPU-bound.

## M0.4 — executed in same session

**Install gotcha.** The PyPI distribution is called `playground`, not
`mujoco-playground`. Imports still use `mujoco_playground`. First
`uv add mujoco-playground` failed; `uv add playground` succeeded. Now
pinned as `playground>=0.2.0` in `pyproject.toml`. Upstream constraints
(`mujoco>=3.6.0`, `mujoco-mjx>=3.6.0`, `warp-lang>=1.11`,
`brax>=0.14.2`) are all satisfied by what M0.2 already installed.

**Env shape — G1JoystickFlatTerrain.**

    env class:       Joystick
    obs_size:        {'privileged_state': (216,), 'state': (103,)}
    action_size:     29
    control dt:      0.02 s (50 Hz)
    reset reward:    0.000,  done=False
    one-step reward: 0.029,  done=False

Dict observation: 103-D asymmetric `state` for the actor, 216-D
`privileged_state` for the critic. 29 actuators — matches the bare G1
actuator count we measured in M0.2.

**Backend confirmation.** Env load prints cascades of
`Module mujoco.mjx.third_party.mujoco_warp._src.*` compilations — Warp
is live and doing the collision + solver work. First-time compile
takes ~60 s on this box (the cholesky-gradient kernel alone is ~35 s).
Kernels are cached under `~/.cache/warp/1.12.1/`, so all subsequent
invocations are near-instant.

**Throughput on the 4060 Ti (8 GB, ~5 GB usable after desktop).**
Each batch size runs in a clean subprocess to avoid cumulative
JAX+Warp VRAM fragmentation — on a single long-lived process, a
second-tested batch size OOMs on tiny 0.5 MB allocations because
previous batches' kernels and state tensors are still resident:

    Parallel envs   Wall for 200 steps   Throughput
           64       5.25 s                2.4 kEnvSteps/s
          256       5.68 s                9.0 kEnvSteps/s
          512       6.38 s               16.1 kEnvSteps/s
         1024       7.89 s               25.9 kEnvSteps/s
         2048      11.76 s               34.8 kEnvSteps/s

Per-env throughput falls as batches grow (38 → 17 env-steps/s/env from
64 → 2048 envs), but aggregate keeps climbing. Sweet-spot for Phase 1
training is probably ~1024 envs — highest per-env efficiency that
still approaches peak aggregate. At 34.8 kEnvSteps/s a 50 M-step PPO
run finishes in ~24 minutes of wall clock. `mujoco_playground`'s
default PPO config will likely dictate a specific batch anyway; we'll
adopt it.

**Orchestration pattern.** `scripts/m04_rollout.py` is now
self-dispatching: top-level invocation is the orchestrator that spawns
one Python subprocess per batch size (`--bench N`), plus one `--probe`
subprocess for the env-shape summary. The pattern is worth reusing —
it gives unambiguous VRAM numbers and avoids the Warp-kernel residue
problem we hit on the first pass.

**Known wart.** `mujoco_playground` cached its own copy of
`mujoco_menagerie` on first env load (into the package install dir),
rather than reusing our submodule at `external/mujoco_menagerie`.
~1.7 GB of duplicated data. Not a blocker; future cleanup can point
playground at our submodule via its config surface.

**Minor.** Added `pyrightconfig.json` in the project root with
`extraPaths = [".venv/lib/python3.12/site-packages"]` so the editor's
Pyright stops reporting "Import jax could not be resolved" on every
edit. The `[tool.pyright]` block in `pyproject.toml` did not suffice
in this environment.

**Status:** M0.4 complete.

### Two upstream incompats worked around

Both patched in `scripts/m1_train.py`:

**1. brax + playground double-wrap.** Manually calling
`wrapper.wrap_for_brax_training(env, ...)` before passing to
`ppo.train` stacks brax's `VmapWrapper` on top of playground's own
vmapping — both try to `vmap` the rng and the second call gets a
scalar key → `TypeError: JAX encountered invalid PRNG key data:
expected key_data.ndim >= 1; got ndim=0`. Upstream
`learning/train_jax_ppo.py` passes unwrapped envs and relies on
`wrap_env_fn=wrapper.wrap_for_brax_training` as a kwarg to `ppo.train`.
Adopted that pattern.

**2. brax 0.14.2 × JAX 0.10 API break.** `brax/training/agents/ppo/train.py`
calls `jax.device_put_replicated`, which JAX 0.10 removed (see
[JAX pmap migration docs](https://docs.jax.dev/en/latest/migrate_pmap.html)).
The immediate failure was an `AttributeError`; after a naive
`jax.device_put` shim, `_unpmap(...).squeeze(0)` then failed because
it expected a size-1 leading device axis. Real fix: shim
`jax.device_put_replicated` to **prepend** a size-1 axis so the
squeeze survives. Brax is "latest-since-March-2025" on PyPI — this is
real drift until upstream updates. Noted in currency-check memory.

## M1-full (Option B with Option-3 tuning) — executed in same session

Enabled three things before launching:

2. `save_checkpoint_path=checkpoints/m1-g1-full` passed to `ppo.train`

Sanity-tested with 128 envs × 50k steps (actually ~3.1M after brax
rollout-padding), 19 mid-training checkpoints landed in
`checkpoints/m1-sanity/`, reward climbed -6.44 → -3.30.

Then launched Option B: `--num_envs 1024 --num_timesteps 100000000
--run_name m1-g1-full`, logging to wandb run `oo2h5y6t`.

### Training progressed well, then crashed at step 48.66 M

Reward climbed **monotonically** — and crucially crossed **zero** by
step 32 M, meaning the policy is actually *earning* the
`tracking_lin_vel` reward (tracking the commanded joystick velocity):

    step          eval_reward   note
        0         -6.47         random init
    5,406,720    -2.94
   10,813,440    -2.58
   16,220,160    -2.32
   21,626,880    -1.83
   27,033,600    -1.50
   32,440,320    +0.77         ← first positive, earning track reward
   37,847,040    +1.56
   43,253,760    +3.70         ← last saved, strong walker
   [48,660,480]  crashed

At step 48.66 M the viz callback OOM'd (caught by the try/except as
designed, so training continued one more step), but the **evaluator
itself then OOM'd on the same 524288-byte allocation** and took the
whole script down with a `JaxRuntimeError`. The pipeline `python ... |
tee` still reported exit 0 (tee succeeded even though Python died);
`pipefail` was not set. Lesson for future runs: always set `pipefail`
or check Python's status directly.

### Root cause

**Cumulative VRAM growth over hours of training on the 4060 Ti.**
JAX XLA caches, Warp kernel caches, and growing checkpoint state all
accumulate; the viz callback's single-env instance piles on another
small allocation per eval. After ~16 minutes the 5 GB of VRAM we had
available (after the desktop's ~3 GB) is fragmented enough that a
524 kB allocation fails. This is the same pattern we first hit in M0.4
when running multiple batch sizes in one process — the robust answer
was subprocess isolation.

### Recovery

`brax.training.checkpoint.load()` can read orbax-format directories.
Extended `scripts/m1_render.py` to accept either a pickle file or an
orbax directory. Pointed it at `checkpoints/m1-g1-full/000043253760/`
(the last checkpoint before the crash, eval_reward +3.70) and rendered
a 10 s rollout.

### What to change before any future long run

- **Don't chain `| tee` without `set -o pipefail`.** Python can die
  silently under it.
- **VRAM hygiene.** Three options, roughly increasing in complexity:
  (a) drop `num_envs` from 1024 to 768 to keep headroom for
  accumulation; (b) disable the viz callback for long runs and use
  mid-training checkpoints rendered out-of-process for progress
  videos; (c) do viz rendering in a subprocess fed via a shared-dir
  queue.
- **Prefer loading the best mid-training checkpoint** as the
  "deliverable" for a crashed run rather than re-training from
  scratch — the policy at 43 M is clearly useful.

## M2 — executed in same session: head camera renders G1's first-person view

**What shipped.** `scripts/m2_head_camera.py`. Adds a first-person
head-mounted camera to G1 via `mujoco.MjSpec` (no submodule edits, no
duplicated MJCF), rolls out the trained M1 policy, renders a 200-frame
head-cam sequence from the 43 M-step checkpoint.

Artifacts:

- `docs/journal/assets/2026-04-16-m2-head-cam-sample.png` — mid-rollout
  frame at 320×240, showing horizon + checkered ground receding into
  distance + sky, user-verified forward-looking.
- `docs/journal/assets/2026-04-16-m2-head-cam-rollout.gif` — 200 frames,
  4 s at 50 fps, ~5.5 MB.

**How the camera is attached.** G1 has no separate head body — the
"head" is a rigid mesh (`head_link`) geom on `torso_link` at offset
(0.0039635, 0, -0.044). We attach the camera to `torso_link` at local
pos (0.10, 0, 0.18), i.e. a bit forward and above torso origin (in the
area where eye-level sits on the head mesh). Camera mode is default
(fixed), attached to the parent body.

**Orientation landmine.** First attempt used quaternion
(0.5, 0.5, -0.5, 0.5). The resulting render showed mostly floor and
G1's own head in frame — camera was pointing wrong. Root cause: my
derived rotation matrix had `det = -1`, i.e. it was a reflection, not
a proper right-handed rotation. Fix: make the camera basis explicitly
right-handed (`cam_x = world -Y`, `cam_y = world +Z`,
`cam_z = cam_x × cam_y = world -X`, so `-cam_z = world +X = forward`),
verified via `mujoco.mju_mat2Quat` / `mju_quat2Mat` round-trip.
Correct quaternion: **(-0.5, -0.5, 0.5, 0.5)** in MuJoCo's
(w, x, y, z) convention. Lesson: for manual rotation-matrix →
quaternion conversions, always check `det(R) = +1` first.

**Why MjSpec, not XML include.** MuJoCo's XML `<include>` merges
top-level elements, but attaching a camera as a child of an already-
closed body (`torso_link` is defined inside the included `g1.xml`) is
awkward. `MjSpec.from_file()` gives a fully mutable Python view of the
model where we can just `spec.body("torso_link").add_camera()`,
compile, and render. Single-source-of-truth stays in the menagerie
submodule; our augmentation lives only in the script.

**Architecture note.** The playground env drives physics unchanged.
Our head-cam-augmented `MjModel` is only used by `mujoco.Renderer`,
fed each step's `qpos` / `qvel` from the playground state. Physics is
not duplicated; only rendering is.

**Status:** M2 complete. The exit criterion was "pixels flow from
G1's first-person view through the pipeline" — met. Formal
`pixels` key in the env observation dict is deferred to M3 / Phase 3,
where it will be coupled to the frozen visual encoder (DINOv3 /
V-JEPA 2.1).

### Late-session update — V-JEPA 2.1

User flagged that **V-JEPA 2.1** (arXiv 2603.14482, Mar 2026,
Mur-Labadia et al., Meta/FAIR) is out and supersedes V-JEPA 2 as the
temporal-encoder candidate. Key changes: dense predictive loss (both
visible and masked tokens contribute), deep self-supervision across
multiple intermediate encoder layers, multi-modal image/video
tokenizers, scaling improvements.

Benchmark that matters for us: **+20 points on real-robot grasping
success rate vs V-JEPA 2 AC.** That's a meaningful gap for any
embodied-AI downstream.

**License caveat:** weights are released under **CC-BY-NC-ND 4.0** —
non-commercial, no-derivatives. For Vitruvian's personal-research
scope this is fine, but the stack should be designed to degrade
gracefully to DINOv3-only (commercial license) if commercial use ever
becomes a concern. ADR 003 addendum updated with this note.
